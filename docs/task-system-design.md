# 项目记忆与任务控制面的分层设计

## 背景

`context-bridge` 原有的 `handoff -> 执行 -> feedback -> current_snapshot` 已经能够保存任务输入和结果，但它缺少统一任务主记录、生命周期、重复执行记录和自动化 Loop。随着项目与 Agent 数量增加，只靠对话或零散 handoff 很难回答“现在有哪些任务、哪项在审核、一次任务执行过几轮”。

## 核心模型

系统把长期事实和运行态事实分开：

```text
Project（长期事实）
└── Workstream（长期工作方向）
    └── Task（有边界的交付目标）
        ├── Run（一次 Agent 执行）
        └── Artifact（handoff、feedback、commit、PR、文档）
```

### Project

Project 解决“这是什么项目、源码在哪里、长期约束是什么、当前阶段处于什么状态”。它没有完成日期，也不因为某张任务卡关闭而结束。

### Workstream

Workstream 解决“项目的工作长期沿着哪些方向发生”。每个注册项目默认有一个 `daily-development` 主 Workstream，承载功能、缺陷和工程治理。专项建设可以增加独立 Workstream。

Workstream 不是永不结束的大 Task，不直接交给 Agent 执行。

### Task

Task 解决“这一轮到底要交付什么”。它必须目标单一、范围明确、可以验收，并最终进入 `done` 或 `cancelled`。

### Run

Run 解决“谁在什么时候执行了哪一次”。评论后的修正、失败重试或换 Agent 执行，都产生新的 Run，但目标不变时仍属于同一 Task。

### Loop

Loop 是 Task 的生产与调度规则，不是任务本身。它可以收集输入、去重、创建卡片、调度低风险任务和检查超时，但不能绕过权限与审核边界。

## 事实源边界

| 信息 | 权威来源 |
|---|---|
| 项目身份、源码仓、设备路径 | `projects/registry/` |
| 稳定事实 | `project_profile.md` |
| 项目当前摘要 | `current_snapshot.md` |
| 长期工作方向 | `workstreams.json` |
| Task、状态、Run、Loop | `tasks/` |
| 冻结的执行输入 | `handoffs/` |
| 正式执行回执 | `feedback/` |
| 代码、测试、提交、PR | 目标源码仓 |

`current_snapshot.md` 可以汇总关键活跃任务，但不复制完整看板。看板也不能反过来覆盖项目稳定事实。

## 为什么不使用一张永久开发任务

永久任务会不断累积评论、执行记录、目标变化和附件，最终重现“一个巨型对话无法追溯”的问题。长期工作用 Workstream 表达，具体工作持续拆成有结束条件的 Task，才能维持上下文边界。

## 风险与无人参与降级

可持续 Loop 的目标不是让所有工作无条件继续，而是按风险降级：

- 低风险：可以自动收集、分析、验证，符合策略时继续。
- 中风险：可以自动产出草稿或补丁，停在 `in_review`。
- 高风险：只产出方案、证据和待确认项，不自动修改生产规则或发布。
- 关键失败：进入 `blocked` 或等待下次调度，不无限重试。

这让系统在无人参与时仍能产生有价值结果，同时保留医疗业务、生产数据和发布动作所需的人类责任节点。

## 演进方向

当前仓库只实现 Git 可追踪的基础协议与 CLI，不实现完整 UI。未来看板或其他工具应把 `tasks/` 当作可同步的任务协议层，而不是取代 `projects/`。
